## 软件质量保障（1）

来源：[Lecture 11](https://jyywiki.cn/GSE/2026/lect11.md)

### 从意图到可观察的失效

意图、规格和实现之间有两道鸿沟。需求可能没有表达真实意图，代码也可能偏离已经写清的规格。本讲关注第二道鸿沟。Agent 能快速修改软件，测试和断言提供判断这些修改是否满足规格的反馈。

| 概念 | 购物车示例 |
| --- | --- |
| 缺陷（fault） | 更新购物车的代码将某项金额重复计入缓存总价。 |
| 错误（error） | 执行到这个分支后，缓存总价与商品明细不一致。 |
| 失效（failure） | 界面读到错误缓存，用户看到的总价偏高。 |

如果结账时从明细重新计算，账单可能正确。要及早发现问题，可以构造触发重复计费的用例，并在更新后断言缓存总价等于明细之和。测试负责触发缺陷，断言把错误状态变成可观察的失败。

### 复现条件也是输入

- 依赖锁文件记录解析后的依赖树。复现还需要记录操作系统、运行时及相关配置。
- 时间、随机数、网络响应、文件内容和线程调度都可能改变结果。两个线程各做一次读取、加一、写回，若都读到初值 0，最终可能只得到 1。
- 一个反例足以推翻普遍性的规格主张。有限测试通过提供的是受测试范围约束的证据。对一个原样返回输入的排序实现，已排序样本会通过，逆序样本可以直接暴露问题。

### 测试范围与选例

以选课为例，各层承担不同的检查：

| 层级 | 检查的问题 |
| --- | --- |
| 单元测试 | 给定学生已修课程与先修规则，判定函数是否返回正确结果？ |
| 集成测试 | 选课服务能否正确读取先修判定和数据库里的课程记录？ |
| 系统测试 | 登录、查询、选课、刷新后，结果是否仍然可见？ |
| 验收测试 | 名额用尽时是否拒绝选课，并给学生明确反馈？ |

黑盒测试从规格选例。用等价类代表相同处理规则，用边界值覆盖规则切换处。例如接口允许 0 至 100 个元素，可以检查 0、1、99、100、101，并为 101 明确预期错误。规则由多个条件共同决定时可列决策表，行为依赖历史时可按状态转换选择操作序列。

白盒测试从实现选例，查看语句、分支和路径是否执行过。覆盖率提供可达性信息。完整用例要准备输入和环境、执行操作，并核对预期结果。例如误将加法写成减法时，输入 `(1, 0)` 即使执行了错误语句也会通过，应选能区分两种实现的输入。

### 把测试接进开发流程

- 测试金字塔通常以快速单元测试为主，用集成测试检查接口，用少量端到端测试走真实流程。各层的数量取决于反馈速度和故障定位成本。
- Stub 提供预设响应，mock 还能核对调用次数、参数等交互约定。支付超时可用替身稳定触发，支付协议本身仍需通过真实集成来验证。
- 修复缺陷时保留能稳定触发问题的用例，确认修复前失败、修复后通过，再交给 CI 持续运行。

### 架构决定哪些行为容易验证

课堂的游戏案例里，Agent 反复通过截图核对界面。截图适合检查画面，弹药扣减、碰撞和胜负规则适合直接检查状态。把规则抽成接收旧状态与动作、返回新状态的函数，就可以单独测试空弹匣、冷却时间和胜负判定。把时钟与随机数来源显式传入，还可以控制测试推进的时间，并重放同一次执行。

### 差分测试、模糊测试与实体设备

- **差分测试**为复杂输出提供比较基准。处理器模拟器可与参考模型从对应状态出发执行相同指令，在首次出现寄存器差异时停下。差异需要对照规格确认责任方，共享误解也可能让两份实现得到相同的错误结果。
- **模糊测试**负责搜索输入。覆盖反馈能保留触达新行为的样本，再以这些样本为起点继续探索。断言失败或与参考模型结果不同，才是需要调查的异常信号。把可复现的输入留下，可以转成回归用例。
- **实体操作自动化**扩展可控输入的范围。讲义的 SD 卡装置可以反复插拔。在测试中安排读写进行时拔卡、随后重插等序列，并记录操作时机和系统响应，就能重放一些靠手动操作难以复现的问题。
